前面已经单独写过一篇文章，介绍这个博客采用的整体方案。这篇就不再重复介绍技术框架，而是记录真正动手搭建和调整的过程。

对于一个个人博客来说，真正耗时间的往往不是“把网站跑起来”，而是后面那些看起来很小的问题：一个链接应该指向哪里，一个分类页面到底应该怎么组织，文章目录怎么跟随滚动，中文文件名是否合适，某个开关为什么没有删除已经发布的文章……

这些事情单独看都不复杂，但往往需要实际踩一次坑才能知道应该怎么处理。下面把这次建站过程中比较有价值的细节记录下来，也给以后继续修改这个博客留一份备忘。

## 一、主题并不是越“专业”越好

最开始尝试过几个 Jekyll 主题，后来实际使用了 Minima。

Minima 本身当然没有问题，而且它是 Jekyll 生态里非常成熟的主题。不过真正放进自己的文章之后，发现它的整体视觉风格比较像传统报刊：信息密度比较高，页面也比较规整。

最后还是回到了 Cayman。

Cayman 的好处是结构简单，页面留白比较充足，而且主题本身并没有太多复杂的功能。对于个人博客来说，这反而方便自己修改。

这次的一个体会是：选择主题的时候，Demo 看起来漂亮并不意味着适合自己。真正重要的是把自己的文章放进去以后，标题、正文、分类、归档和侧边栏是否舒服。

主题只要结构足够简单，后续自己修改 CSS 往往比不停寻找“完美主题”更省事。

## 二、导航栏不是创建了页面就会自动出现

最开始创建了“关于”“联系”“分类”“归档”“标签”等页面，结果发现它们并没有按照预期全部出现在顶部导航栏。

后来才发现，Cayman 的导航并不是单纯根据页面文件自动生成的，而是受到 `_config.yml` 中相关页面引用设置的控制。

也就是说，页面存在和页面出现在导航栏，是两件事情。

这个问题本身很简单，但很容易让人产生误判：明明 `about.md` 已经存在，为什么网站导航里没有“关于”？

遇到这种情况，应该先检查主题的导航配置，而不是重新创建页面。

## 三、分类页面最后没有采用“一个分类一个页面”

Jekyll 本身很适合生成分类页面，最直观的想法就是：

```text
/categories/游戏/
/categories/读书/
/categories/杂谈/
```

每个分类拥有一个独立页面。

一开始也考虑过这种方式，但对于目前这个博客来说，感觉有些过度设计。

文章数量并不大，如果每个分类都生成一个页面，网站结构会变得比较复杂，而且还要考虑模板、分页和链接维护。

最后采用了一个更简单的方案：

```text
/categories.html
```

一个页面列出所有分类，每个分类下面直接列出属于它的文章。

这样进入分类页面以后，可以一次看到整个博客的分类结构。

同时，为了让侧边栏能够直接跳到对应分类，在分类标题上增加了锚点：

```liquid
<h2 id="category-{{ category[0] | slugify }}">
    {{ category[0] }}
</h2>
```

于是链接可以写成：

```liquid
{% assign category_slug = category[0] | slugify %}
<a href="{{ "/categories.html#category-" | append: category_slug | relative_url }}">
    {{ category[0] }}
</a>
```

最终效果就是：

```text
分类
├── 游戏
├── 读书
├── 杂谈
└── ……

点击“游戏”
↓
/categories.html#category-游戏
↓
直接跳到“游戏”这一栏
```

对于文章数量不多的个人博客，这种方式简单很多。

## 四、标签页面采用了和分类页面一样的结构

标签其实和分类面临着类似的问题。

最开始标签页面是一列一个标签，每个标签之间留了比较大的空间。实际看起来比较松散。

后来直接把它改成和分类页面一样的两列布局。

每个标签作为一个小标题，下面紧凑地列出相关文章。

这样分类和标签虽然承担不同的作用，但视觉结构保持一致，整个网站也更加统一。

同时，标签也采用锚点跳转：

```liquid
<div class="tag-item" id="tag-{{ tag[0] | slugify }}">
```

对应的链接：

```liquid
{% assign tag_slug = tag[0] | slugify %}
<a href="{{ "/tags.html#tag-" | append: tag_slug | relative_url }}">
    {{ tag[0] }}
</a>
```

这也是一个比较实用的思路：当网站内容量还不大时，没有必要为每一个分类、标签都建立独立页面。

## 五、归档最终选择了按年份

归档页面也没有继续细分到月份。

现在的结构是：

```text
归档
├── 2026
├── 2027
└── 2028
```

点击某一年以后，进入对应年份的文章列表。

例如：

```text
/archive/2026/
```

页面中按照日期列出这一年所有文章。

对于个人博客来说，年份通常已经足够。月份归档在文章数量很大的博客里比较有意义，但如果一年只有几十篇文章，继续拆分反而增加了浏览成本。

所以这里采取了一个很简单的原则：

文章少的时候，结构宁可简单一点。

## 六、文章文件名和文章标题最好分开

这是这套发布流程里一个比较重要的细节。

文章标题可以正常使用中文：

```yaml
title: 我为什么重新开始写博客
```

但文件名采用英文、数字和短横线：

```text
2026-09-18-restart-blog.md
```

而不是直接把中文标题作为文件名。

这样做的好处主要是 URL 更容易阅读和复制，也减少了一些中文文件名在不同工具之间传递时可能出现的问题。

因此现在的文章实际上存在两个概念：

```text
title
文章真正显示给读者的标题

filename
文章在网站和文件系统中的标识
```

两者没有必要强行保持一致。

## 七、`share: false` 不代表已经发布的文章会自动消失

这是一个很容易误解的地方。

在 Obsidian 中，一篇文章可以通过：

```yaml
share: true
```

决定是否发布。

后来如果把它改成：

```yaml
share: false
```

它不会自动把已经存在于 Jekyll `_posts` 目录中的文章删除。

原因很简单：发布系统负责把文章发布出去，但“停止发布”和“删除以前已经生成的文件”并不是完全相同的操作。

因此，如果一篇文章以前已经发布过，后来决定彻底从网站删除，需要检查 Jekyll 仓库中的 `_posts` 目录，并手动删除对应文件，然后提交更新。

这个问题值得记下来，因为以后如果突然发现“我明明把 share 改成 false 了，为什么网站上还有这篇文章”，原因就在这里。

## 八、首页摘要遇到 Markdown，是一个很典型的小坑

首页目前会列出所有文章，并显示一段摘要。

最初使用的是：

```liquid
{{ post.excerpt | markdownify | truncatewords: 30 }}
```

看起来非常合理：先把文章摘要转换成 Markdown，再截取一定长度。

但实际使用以后发现，如果文章开头本身就是一个 Markdown 标题，例如：

```markdown
## 为什么我不喜欢……
```

那么首页摘要也会把它当成标题重新渲染。

结果就是首页的文章列表中突然出现一个和文章标题层级不一致的小标题，视觉上很奇怪。

最后改成直接去除 HTML 和换行，只显示纯文本：

```liquid
{{ post.excerpt | strip_html | strip_newlines | truncatewords: 30 }}
```

这也提醒了一个问题：

首页摘要和正文是两种不同的展示场景。

正文需要正确解析 Markdown，而首页摘要通常只需要“看起来像一段简介”。把正文的 Markdown 格式原样带到摘要里，未必是好事。

## 九、文章页面的分类和标签最好直接成为导航入口

文章页除了正文之外，还显示文章所属分类和标签。

这些文字本身也可以成为链接。

例如分类直接跳转到分类总页面中对应的位置，标签则跳转到标签总页面中对应的位置。

这样文章页、分类页、标签页之间就形成了一个完整的导航关系：

```text
文章
 ↓
分类
 ↓
该分类下的所有文章

文章
 ↓
标签
 ↓
使用该标签的所有文章
```

相比单纯显示几个不能点击的文字，这样更有实际用途。

## 十、侧边栏最后形成了“三栏结构”

文章页面最后采用了比较典型的三栏布局：

```text
┌────────┬──────────────────────────┬──────────┐
│        │                          │          │
│  目录  │          正文            │ 网站导航 │
│        │                          │          │
│        │                          │ 分类     │
│        │                          │ 标签     │
│        │                          │ 归档     │
└────────┴──────────────────────────┴──────────┘
```

左边是文章目录，中间是正文，右边是网站导航。

而普通页面没有文章目录，因此变成两栏：

```text
┌──────────────────────────────┬──────────┐
│                              │          │
│            页面              │ 网站导航 │
│                              │          │
└──────────────────────────────┴──────────┘
```

这里没有使用特别复杂的布局框架，直接用 CSS Grid 就足够了。

一个个人博客其实不太需要复杂的前端框架。只要把页面结构想清楚，几十行 CSS 就能完成相当不错的布局。

## 十一、文章目录是这次最折腾的一个小功能

左侧文章目录看起来是一个很简单的功能：读取文章中的 `h2`、`h3` 等标题，然后生成链接。

实际做起来却有几个细节。

首先，需要自动给没有 ID 的标题生成 ID。

其次，不同级别的标题需要有不同的缩进：

```text
第一章
    第一节
        小节
    第二节
第二章
```

所以目录中的链接根据 `h2`、`h3`、`h4` 等分别设置不同的缩进和字号。

然后又增加了当前阅读位置高亮。

当页面向下滚动时，当前所在章节会在左侧目录中变成粗体。

真正麻烦的是：左侧目录本身高度有限，如果文章很长，当前章节可能已经滚出目录区域。

最开始尝试使用 JavaScript 的 `scrollIntoView()` 来自动滚动目录。

结果发现，这个方法不仅会影响目录本身，还可能让整个网页的主滚动位置发生变化，页面滚动起来非常奇怪。

最后没有继续使用 `scrollIntoView()`，而是直接操作左侧目录容器自己的：

```javascript
sidebar.scrollTop
```

只让目录侧栏自己滚动，不干扰正文页面。

这是一个很小但很典型的前端问题：

“让某个元素滚动”和“让包含这个元素的页面滚动”在浏览器里并不是一回事。

最后采用手动控制侧栏滚动的位置，效果就稳定了。

## 十二、中文标题的目录 ID 也需要考虑

自动生成目录的时候，还需要给标题生成 HTML 的 `id`。

例如：

```text
为什么我不喜欢大型开放世界游戏？
```

需要转换成可以用于锚点跳转的 ID。

同时还要考虑同一篇文章中出现两个相同标题的情况。

如果两个标题最终得到相同的 ID，就需要自动增加：

```text
标题
标题-1
标题-2
```

否则点击目录链接时，浏览器无法准确判断应该跳到哪一个标题。

虽然这只是几行 JavaScript，但属于只有真正使用长文章以后才容易发现的问题。

## 十三、右侧栏没有堆太多功能

右侧栏目前主要保留：

```text
回到首页    回到顶部

分类
……

标签
……

归档
……
```

没有继续塞入天气、最新评论、热门文章、友情链接、社交媒体等东西。

一开始做博客的时候，很容易觉得“既然有侧边栏，就应该把能放的东西都放进去”。

但实际使用以后，侧边栏最重要的是帮助读者导航，而不是填满空白。

因此最后还是尽量保持简单。

## 十四、回到顶部其实不需要复杂的 JavaScript

“回到顶部”最后直接利用页面顶部的锚点实现。

在：

```html
<body id="top">
```

然后链接：

```html
<a href="#top">回到顶部</a>
```

就可以了。

原本可以用 JavaScript 做平滑滚动，但这里完全没有必要。

这次建站过程中一个比较明显的体会就是：

能用 HTML 解决的问题，就没必要为了它再增加 JavaScript。

## 十五、移动端没有单独做一套网站

桌面端最终使用三栏布局，但手机显然不适合把三个栏目硬挤在一起。

因此在较窄屏幕下，CSS 会自动取消左侧目录，把右侧栏移动到正文下面。

也就是说：

桌面端：

```text
目录 | 正文 | 导航
```

手机端：

```text
正文
↓
导航
```

这样已经足够。

个人博客的移动端访问主要还是阅读文章，没有必要为了一个简单博客专门维护一套复杂的移动端页面。

## 十六、首页、分类、标签和归档最终形成了不同的阅读方式

到这里，网站实际上已经有了四种不同的文章入口。

首页适合看最新文章：

```text
文章
摘要
文章
摘要
文章
摘要
```

分类页适合按照主题寻找文章。

标签页适合按照关键词寻找文章。

归档页则适合按照时间回顾。

这四种方式各自承担不同的作用，因此没有必要把所有内容都塞进首页。

## 十七、最后没有急着增加搜索、分页和各种插件

现在文章数量还不多，所以暂时没有增加站内搜索，也没有做分页。

同样没有继续增加评论、点赞、文章推荐、复杂的统计组件等功能。

这些东西以后当然都可以做，但现在增加它们，解决的更多是“网站看起来像一个完整网站”的心理需求，而不是实际的阅读需求。

对于一个个人博客来说，文章数量真正增长以后，再根据实际需要增加功能，会比一开始把所有功能都搭起来更合理。

例如：

文章达到几十篇以后，可能开始需要搜索；

文章达到几百篇以后，可能需要分页；

如果开始有稳定读者，再考虑评论和统计。

功能应该随着内容增长，而不是让内容去迁就功能。

## 十八、这次建站留下的一些经验

整个过程中真正花时间的地方，大多数都不是 Jekyll 本身，而是各种“小问题”。

一个页面应该怎么组织；
一个链接应该跳到哪里；
分类是否需要独立页面；
标签是不是应该和分类保持一致；
目录滚动到底应该滚动哪里；
Markdown 摘要到底应该如何显示；
一个已经发布的文件为什么没有自动消失。

这些问题没有一个特别高深，但它们决定了最后的网站是不是“顺手”。

对于这种规模的个人博客，我最后比较认同的一条原则是：

**先把结构做简单，再一点一点解决真正遇到的问题。**

没有必要一开始就把搜索、分页、评论、统计、复杂主题和各种自动化全部加入。

能稳定发布文章，页面看着舒服，文章之间能够通过分类、标签和归档互相找到，手机上能够正常阅读，这些其实已经足够构成一个完整的个人博客。

剩下的功能，等以后真的需要的时候再加。

毕竟博客最重要的东西，最终还是文章本身。
